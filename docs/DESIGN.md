# 品触れ（Shinafure）設計メモ

**盗まれたデータが AI に入った瞬間に、持ち主に知らせる。**

古物商は、警察から回ってくる「品触れ」（盗品の手配書）と持ち込まれた品物を照らし合わせます。これを AI の世界に移したのが品触れです。

1. 企業は、自社の顧客データに**偽の顧客（カナリア）**を混ぜます。
2. その「手配書」を台帳に登録します。
3. AI の提供者や AI ゲートウェイは、推論への入力を台帳と照合します。

盗んだ名簿を AI で整形・名寄せ・分析したり、恐喝文を作ったりした時点で、データの持ち主に通知が届きます。

## 1. 突いている盲点

- 2026年の攻撃者は、盗んだデータの後処理に AI を使っています。CrowdStrike の調査では、攻撃者の環境から Claude Code のセッション履歴が見つかっています。
- 既存の「おとりデータ」は、すべて**データの持ち主が自分の監視範囲の中で**見張るものです。盗まれて外に出た後は、持ち主からは見えません。
- 品触れは、盗品が必ず通る**第三者の作業台（AI 提供者）**を照会点にします。構造が一番近いのは GitHub の secret scanning パートナープログラム（GitHub が公開リポジトリを走査し、漏れたトークンを発行元に知らせる仕組み）です。走査対象を「推論入力」に、登録者を「データの持ち主」に置き換えた形です。

## 2. 仕組み

**カナリア（`shinafure/canary.py`）**
- 実在しそうだが誰とも重ならない人物を作ります。氏名は珍しい実在の姓と名の組み合わせで、漢字・カナ・ローマ字の3つの表記を持たせます。
- メールは自社が管理するドメインに乱数を付けます。電話番号は、**本番では自社が保有する番号**を使います。

**照合用トークン（`shinafure/tokens.py`）**
- 強いトークン：メール、電話番号（どの書式でも同じ値に正規化）。
- 弱いトークン：氏名（漢字・カタカナ・ひらがな・順不同のローマ字）、住所（「9丁目17番3号」と「9-17-3」を同一視）。
- 判定ルールは次のとおりです。
  - 強いトークンが1つでも一致したら**確定**。
  - 氏名と住所がそろったら**確定**。
  - 1つの入力に**別々のカナリアの氏名が2人分以上**あったら**確定**。偶然には起きないためです。
  - 氏名が1人分だけなら**疑い**として扱い、通知しません。

**台帳（`shinafure/registry.py`）**
- 台帳は**平文を一切持ちません。** 鍵付きの一方向関数 F(t) = SHA256(k·H(t)) の値だけを持ちます。鍵 k は台帳だけが知っています。
- 登録者は、自分のトークンを目隠し（ブラインド）してから F を計算してもらいます。台帳は何を登録されたのか分かりません（OPRF という暗号の仕組み）。
- 提供者は、24ビットの接頭辞フィルタで入力を手元でふるいにかけます。通過したものだけを目隠しして台帳に問い合わせます。**プロンプトの中身は台帳に出ません。**
- 問い合わせの回数は提供者ごとに制限します。台帳を「この値はカナリアか？」を調べる道具に使わせないためです。
- 通知に含まれるのは、カナリアID・データセット名・提供者名・時刻だけです。

この方式は、Google の Password Checkup（漏えいしたパスワードを、目隠しと接頭辞で照会する仕組み）と同じ考え方を、カナリア人物に応用したものです。

**プロキシ（`shinafure/proxy.py`）**
- OpenAI 互換の `/v1/chat/completions` です。確定ヒット時は、記録して通す（`flag`）か、拒否する（`block`）かを選べます。

### 処理速度と規模

- **日本語は遅いです**（純Pythonで約19万文字/秒）。名前の候補を、全ての部分文字列で作っているためです。1万文字のプロンプトで約50msかかります。本番では、ネイティブ実装か、形態素解析で名前らしい部分だけに候補を絞る必要があります。
- 台帳に登録されるトークンが増えるほど、接頭辞フィルタを通過する無関係な候補が増えます（`results.md` の第3節に計算表）。100万トークン規模なら、接頭辞を32ビットにすれば、日本語1万文字あたり約10回の照会で済みます。
- **ただし、接頭辞が長いほど、フィルタが漏れたときの危険が大きくなります。** 攻撃者は、フィルタに当たる行を捨てるだけで、ほぼ正確にカナリアを除去できます。フィルタは参加する提供者だけに渡し、絶対に公開しないことが前提です。

## 4. 限界（正直に）

- **参加しない AI には効きません。** 自前で動かすモデル（DeepSeek などのオープンなモデルをローカルで運用）、参加していない提供者、データを AI に入れない攻撃者には無力です。単独では決定打になりません。
- **見破られる手がかりが残ります。** デモはカナリアのメールを1つのドメインにまとめています。気づいた攻撃者は行ごと削除できます（実測で0/10）。本番では、普通に見える複数のドメインと、自社が保有する実在の電話番号を使う必要があります。
- **名前と名字が分かれると検出できません**（家族ごとの名寄せで0/10）。要約されて個人の値が消えた場合も同じです。
- **実際の LLM では測っていません。** 変換は、それを模した決定的な処理です。本物のモデルに整形させたときの耐性は未測定です（API キーがあれば次に測れます）。
- **登録値の検証は v0.4 で入れました**（下の「v0.4 の変更」）。残る穴は、試作の名前・住所の表が小さいこと（偶然一致の上限が高い）と、番号ブロックの確認が SMS 1回であることです。
- **法務の検討が必須です。** 提供者が利用者の入力を照合することについて、プライバシーポリシーや（日本なら）通信の秘密との整理が要ります。
- **台帳が新しい共通の依存先になります。** 運営主体の信頼性と冗長性が問題になります。
- **デモの電話番号は乱数の070番号です。** 実在の誰かの番号と一致しうるので、本番では使えません。

### 本物の LLM での耐性テスト（自分の PC で実行）

多段の処理を想定したテストです。攻撃者がある AI で名簿を整形し、その結果を別の AI に渡す状況で、整形した後にもカナリアが残るかを測ります。データはすべて合成です。

**おすすめは Ollama でのローカル実行です。** 無料で、アカウントも利用枠もなく、データが PC の外に出ません。攻撃者が手元のモデルで前処理する状況にも近いです。

Windows（PowerShell）の場合：

```powershell
# 1. https://ollama.com から Windows 版をインストールし、モデルを取得（約4.7GB）
ollama pull qwen2.5:7b
# 2. zip を展開した shinafure フォルダで
py -m pip install faker fastapi httpx
$env:PYTHONUTF8 = "1"
py -m demo.llm_eval --backend ollama --chunks 4 --rows 20
# 3. 結果は results_llm.md。中断しても同じコマンドで続きから再開できる
py -m demo.llm_eval --report-only
```

- 内容：カナリア入り4ブロック＋カナリアなし4ブロック（各20行）に8種類の指示を出して、64回呼び出します。指示は、JSON化、列の抜き出し（2種）、英訳とローマ字化、家族ごとの名寄せ、電話番号の統一、要約、宛名リスト作りです。
- 所要時間：GPU があれば数十分、CPU だけだと数時間かかることがあります。遅ければ `--model qwen2.5:3b` に下げてください（qwen2.5:3b は研究用ライセンス）。
- 他の方法：Gemini API（`--backend gemini-api`）と Antigravity CLI（`--backend agy`）も使えますが、どちらも**18歳以上**が利用条件です。

### 実測：20人ずつと、周りの本物の行との比較（2026年11月5日）

| | 出力に残った | 同じ出力での普通の顧客の行 | 差の検定（Fisher） |
|---|---:|---:|---:|
| 珍しい名前のカナリア | 11/20（55%） | 635/780（81%） | **p=0.007** |
| 普通の名前のカナリア | 15/20（75%） | 593/760（78%） | p=0.78 |

- **珍しい名前のカナリアは、周りの本物の顧客より明らかに多く消されました。** 普通の名前のカナリアは、本物の顧客と同じ割合でしか消されていません。
- **カナリアは、守るデータの名前の分布に溶け込ませる必要があります。** 目立つカナリアは、AI による前処理で選んで落とされます。
- 出力に残ったカナリアは26人全員を検出し、誤検知は39回中0件でした。
- 普通の名前のカナリアが消える割合は約25%です。10人入れておけば、全員が消える確率は約100万分の1です（行が独立に消えると仮定した場合）。
- 注意点が2つあります。
  - 同じブロックの行どうしは独立ではないので、p値はやや楽観的です。
  - 測ったのは1つのモデル（qwen2.5:7b）と1種類の指示だけです。
- これを受けて、v0.3 から `make_canaries` の既定を `mixed`（8割が普通の名前、2割が珍しい名前）にしました。珍しい名前を一部残しているのは、氏名だけを抜き出された場合の検出（2人分で確定）のためです。

## v0.4 の変更：狙い撃ちできないカナリア（`shinafure/issuance.py`）

品触れは、登録した値が AI の入力に出たら登録者に知らせます。ストーカーが実在の人のメールや氏名＋住所を登録すれば、追跡の道具になります。台帳は登録内容を見られない（目隠し登録）ので、登録時に中身を検査できません。そこで、**通知の前に**検査します。

1. **所有確認**：登録者は、メールのドメインを DNS の TXT レコードで、電話番号のブロックを「ブロック内のランダムな番号に送ったコード」で確認します。
2. **チケット**：登録者はまず開示値（秘密 s、ドメイン、番号ブロック、珍しい名前の割合）にコミットし、その後で台帳から乱数 r を受け取ります。カナリアは H(r‖s) から決定的に作るので、登録者は氏名も住所も番号も選べません。やり直しはチケットの枚数（既定で1日100枚）に限られます。
3. **封印した開示**：カナリアの手がかり t ごとに、開示値を k·H(t) から作った鍵で暗号化して預けます。台帳が持つのは F(t)=SHA256(k·H(t)) で、k·H(t) そのものではないので、提供者が実際に t を見て鍵を渡すまで、台帳にも開けません（サーバの OPRF でメッセージから鍵を作るのは DupLESS と同じ構成です）。
4. **通知前の検査**：確定一致の報告が来たら、台帳は預かった開示を開け、カナリアを作り直し、そのチケットに登録された手がかりがすべてそのカナリアのものか、ドメインと番号ブロックが確認済みかを調べます。通ったときだけ通知します。失敗しても登録者から見える変化はありません（問い合わせや停止は、それ自体が「標的のデータが出た」という合図になるため）。記録は運営者の確認用ログに残します。

`python -m demo.abuse` の結果：

| 試み | 提供者の照合 | 登録者への通知 | 台帳の判断（登録者には見えない） |
| --- | --- | --- | --- |
| 正規：自社カナリアのメールが入力に出る | 一致 | 届いた | |
| 悪用：実在の人のメールをチケットに紛れ込ませる | 一致 | 届かない | チケットのカナリアにない手がかり |
| 悪用：実在の人の氏名と住所を紛れ込ませる | 一致 | 届かない | チケットのカナリアにない手がかり |
| 悪用：所有を確認していないドメインでカナリアを作る | 一致 | 届かない | ドメインが未確認 |
| 悪用：所有を確認していない番号ブロックでカナリアを作る | 一致 | 届かない | 番号ブロックが未確認 |
| 悪用：1枚のチケットに手がかりを足す | - | 登録を拒否 | 1人分の手がかりの上限（8個）を超える |

**残る穴：偶然一致。** 正規のチケットから生まれたカナリアが、たまたま実在の人と同じ氏名と住所になることはありえます。特定の1人に当たる確率は、最大で「引いたチケットの枚数 ÷（名前の数 × 住所の数）」です。試作の表は、珍しい名前の割合を100%にコミットされると氏名400通り×住所4万3,200通りなので、1日100枚を1年引き続けると最大約0.21%です（36,500 ÷ 1,728万）。本番では実在の分布に沿った大きな表が必要です。

その他：
- 台帳の項目を「F → 1件」から「F → 複数件」に直しました。普通の名前は複数のカナリアで重なるため、以前は後から登録したものが前のものを上書きしていました。
- 実験用のデモ（`demo/measure.py`、`demo/llm_eval.py`、`demo/pool.py`）は、結果を再現できるよう `Registry(require_tickets=False)` で手作りのカナリアを使います。既定は `require_tickets=True` です。

## v0.5 の変更：照合を約14倍速く（`shinafure/fastscan.py`、`shinafure/group.py`）

カナリア1,000人を登録した状態で、v0.4 の照合は日本語で毎秒約5万文字でした。プロファイルでは、時間の約4割が接頭辞フィルタの偶然一致による OPRF（純 Python の楕円曲線計算、1回約5ミリ秒）、残りの大半が日本語の名前候補（1文字あたり約4個）を1つずつ SHA-256 にかける処理でした。

1. **x 座標だけの OPRF**：F(t) = SHA256(x(k·H(t)))、開示の鍵も同じ x から作ります。y の符号は結果に影響しません（x(a·(±Q)) = x(a·Q)）。そのため、掛け算を OpenSSL の ECDH（1回約0.07ミリ秒）で行えます。`cryptography` が無い環境では純 Python で同じ値を計算します（`SHINAFURE_PURE=1` で強制）。通信路に流れる要素は32バイトの x 座標です。
2. **名前候補の接頭辞を多項式ハッシュに**：h = (SEED + L)·B^L + Σ c_i·B^(L-1-i) mod 2^64 を splitmix64 で混ぜ、上位32ビットを接頭辞にします。テキスト全体の全ウィンドウ（長さ3〜10）を numpy で一度に計算し、フィルタ（ソート済み配列）と照合します。numpy が無いときは同じ値を Python で計算します。名前以外の候補（e:, p:, t:, a:, r:）は数が少ないので SHA-256 のままです。
3. **接頭辞を32ビットに**：偶然通る候補が256分の1になります。漏れたフィルタが「この値はカナリアか」の判定に使える点は、24ビットでも同じです（登録数が少ない間は24ビットでもほぼ完全な判定器になる）。
4. **F の一覧を提供者が持つ**：`Registry.f_values()`。OPRF の結果を手元の一覧と比べ、一致したときだけ `lookup()` を呼びます。v0.4 では偶然一致した候補の F も台帳に届き、鍵 k を持つ台帳はありふれた名前を当てはめて推測できました。

検証：`tests/test_fastscan.py`（7本）で、numpy と Python の名前候補が参照実装（`tokens.candidates()`）と完全に一致すること、OpenSSL と純 Python の OPRF が同じ値になること（片方で目隠しし、もう片方で評価しても一致）、一致しない候補が `lookup()` に届かないことを確かめています。`demo/bench.py` では、5種類のテキストで候補数・確定・疑いが v0.4 と一致しました。

| KNBC（日本語） | 6.1万 | 164万 | 27倍 |
